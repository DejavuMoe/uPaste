# Threat model

## Scope and trust boundaries

Protected assets include Share content, owner capabilities, encryption keys, service availability, persistence integrity, and application-origin authority. Boundaries are browser-to-app, browser-to-file-origin, reverse-proxy-to-listeners, process-to-database/filesystem, operator/backup access, and third-party networks. Phase 3 exposes anonymous Standard and Encrypted Text creation, read, owner update, and delete in addition to Standard raw and `/healthz`. Strict payload validation, expiration enforcement, capability verification, and inert delivery are implemented. Rate limiting and public-instance abuse controls are not, so unrestricted Internet exposure is not production-ready.

Encrypted Text Shares hide plaintext from the application server when correctly used; V1 File Shares are Standard only. Encrypted text does **not** hide metadata the server necessarily observes: ciphertext size, timestamps, resource ID, expiration, request IP/headers, access timing, and traffic relationships. A malicious administrator can alter served JavaScript and steal future plaintext or keys; browser-delivered zero knowledge cannot prevent that.

## Threat analysis

| Threat | Asset and trust boundary | Attack and impact | Planned mitigation |
|---|---|---|---|
| Stored XSS | Application origin; stored text to viewer browser | Persisted script executes for later readers, stealing capabilities or acting as the app | Phase 2 JSON uses standard escaping and raw delivery is `text/plain`, `nosniff`, sandboxed CSP with no rendering. Markdown HTML remains disabled; any future rendered output requires sanitization. |
| Reflected XSS | Request input to app response | Crafted URL/input is reflected as executable markup | Context-aware framework escaping, no unsafe HTML sinks, CSP, and tests for reflected inputs. |
| Markdown injection / unsafe HTML | Markdown parser/render boundary | Links, raw HTML, or malformed markup create script or deceptive content | Disable raw HTML, sanitize renderer output independently, constrain URL schemes, and keep rendering non-executable. |
| Malicious SVG/HTML/JS/XML uploads | File origin to browser | Active content executes and attempts origin-level compromise | Separate origin and listener, default `Content-Disposition: attachment`, explicit safe-inline allowlist, CSP, and no app-origin file delivery. |
| MIME confusion | Upload input and file response | Extension or declared type tricks browser into executing active content | Inspect bytes where feasible, distrust names/client MIME, use server-selected type, `nosniff`, and attachment by default. |
| Path traversal | Configured data path and future resource names to filesystem | `../`, encoding, symlinks, or wrong filesystem types trick reads/writes | Phase 1 normalizes the configured data path, uses a fixed database filename, rejects a database symlink/non-regular file, and creates restrictive paths. Future payload storage will use server-generated opaque names and canonical root checks. |
| Resource ID enumeration | Public network to Share reads | Guessing IDs reveals Standard Shares | Independent 128-bit `crypto/rand` IDs encoded as 22-character unpadded base64url and generic failures; IDs remain identifiers, never authorization secrets. Rate controls remain future work. |
| Owner-token theft | Browser/app management boundary | Stolen capability permits deletion or other owner actions | Independent 256-bit `crypto/rand` token with `up_o1_` prefix, HTTPS, bearer header only, least-power operations, no persistence of raw token, and constant-time verifier comparison. |
| Token leakage through URLs | Browser history, Referer, logs, analytics | Credential in URL propagates to third parties and infrastructure | Management reads only one Authorization bearer header; query/path/body/cookie tokens are ignored. Creation `Location` contains only the public ID. |
| Logging leakage | Requests/errors to operators and log systems | Sensitive headers or bodies are recorded | Structured logs contain safe operation context only; handlers never log bodies or Authorization, and `OwnerToken` implements redacted `slog` formatting. Regression tests ensure generated, valid, and invalid owner candidates and parser input do not appear in logs/errors. |
| Database theft | Filesystem/backup to attacker | Standard content, Encrypted ciphertext, metadata, and SHA-256 owner-token verifiers are exposed | New data directories/database files use `0700`/`0600`; deployments still require least privilege and protected backups. Uniform 256-bit owner tokens make offline preimage search infeasible without a pepper; content and metadata exposure remains documented. |
| Malicious server administrator | Host/operator to process, files, and served frontend | Reads Standard content/metadata or modifies frontend to capture encrypted plaintext/key | Encrypted mode keeps reviewed-protocol plaintext out of storage, but cannot protect against malicious JavaScript served by that administrator. Disclose limits and pursue secure/reproducible releases and TLS/integrity operations. |
| Brute force | Public network to IDs/tokens | Repeated guesses discover Shares or capabilities | 128-bit random IDs, independent 256-bit random owner tokens, constant-time SHA-256 verifier comparison, and generic responses. Rate limiting and monitoring remain required before unrestricted Internet exposure. |
| Upload/storage abuse | Anonymous client to disk | Fills disk, stores prohibited payloads, or creates excessive objects | Strict per-request/file limits, quotas or rate controls, expiration policy, capacity monitoring, atomic cleanup, and fail closed when capacity is exhausted. |
| Request flooding / DoS | Public network to listeners | Connections or expensive requests exhaust CPU, memory, descriptors | HTTP timeouts, body/connection limits, reverse-proxy limits, bounded concurrency where measured, and operational monitoring. |
| Oversized or ambiguous JSON | Client to parser/memory/disk and authorization boundary | Unbounded, duplicate, invalid-UTF-8, or differently cased input causes exhaustion or inconsistent interpretation | A bounded reader rejects JSON wire bodies above 2 MiB; strict Go JSON v2 rejects duplicate names, invalid UTF-8, unknown/case-mismatched members, malformed JSON, and trailing values; decoded text and SQL are limited to 1 MiB. Owner verification precedes PATCH body processing and is repeated transactionally. |
| Decompression/resource bombs | Uploaded/encoded data to processors | Tiny input expands or consumes excessive parser resources | Do not auto-extract archives; bound compressed and expanded input/time for any future processing; reject unsupported content encodings. |
| CSRF | Third-party site to management API | Browser is induced to perform owner action | No auth cookies; bearer token in an explicit header; same-origin API; validate Origin on sensitive browser requests where applicable. |
| CORS mistakes | Foreign origin to API | Permissive policy exposes responses or enables credential use | Send no permissive CORS by default; explicit narrow allowlist only after a documented use case; never reflect arbitrary origins. |
| SSRF | User input to server outbound network | Server fetch reaches metadata/internal services | No URL fetching or server-side previews; avoid outbound fetch features. If scope changes, use strict destination and redirect controls. |
| Unsafe redirects | User-controlled target to browser | Open redirect enables phishing or leaks fragment/query data | Avoid user-controlled redirects; permit only validated local paths or explicit origins; never forward capabilities. |
| Reverse-proxy trust | Proxy to loopback listeners | Misrouting exposes file content on app origin or bypasses scheme/client controls | Separate listeners and origins, bind loopback by default, explicit proxy routes, TLS at trusted proxy, and deployment tests. |
| Spoofed forwarded headers | Client/proxy to app | Forged IP/proto/host bypasses controls or poisons links/logs | Ignore forwarded headers unless request comes from configured trusted proxies; do not derive security separation solely from `Host`. |
| Fragment theft | Browser history/sync, clipboard, screenshots, extensions, page JavaScript | Complete Encrypted Share URL reveals its AES key and plaintext | Keep the key only in the URL fragment, never send/store it server-side or in browser storage, minimize third-party code, and disclose that anyone with the complete URL can decrypt. |
| Nonce reuse | Browser crypto boundary | Reusing a GCM nonce with one key can destroy confidentiality/integrity | Official helper generates a fresh independent 96-bit nonce for every create/update encryption. Server validates length but cannot prove uniqueness or client key reuse. |
| Ciphertext tampering | Storage/network to browser | Modified payload is shown as authentic text | AES-256-GCM with a 128-bit tag and frozen AAD; decryption rejects changed nonce, ciphertext, tag, envelope, format, or UTF-8. |
| Stale/expired access | Clock/database to read/mutation paths | Content remains readable or is revived after expiration/deletion | Shared active loading derives `now >= expires_at` from one injected server clock on JSON/raw/mutations. Expired rows return 410 and cannot be revived/deleted; owner delete physically cascades payload removal. |
| Cleanup failures | Database/object lifecycle boundary | Expired metadata and payload diverge, leaking content or consuming disk | Read-path expiration enforces inaccessibility first; idempotent retryable purge, reconciliation, and alerts; backup retention documented separately. |

## Residual risks

Traffic analysis and server-visible metadata remain. Availability cannot be guaranteed against an attacker with enough resources. Host compromise defeats Standard privacy and can compromise future browser sessions. Operational backup deletion is controlled by deployers, not the Share lifecycle engine.
